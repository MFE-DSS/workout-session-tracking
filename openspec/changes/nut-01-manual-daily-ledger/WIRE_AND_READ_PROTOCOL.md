12novembre2026, proposition avant GO. Complément normatif du design/PERSISTENCE. Ces décisions techniques ferment R1–R5 de la revue préalable ; elles ne sont pas des comportements implémentés ou vérifiés.

## R1 — accord CAS sans nouvelle table
Service nutrition_consent propre, finaliténutrition_manual et wordingversion1 distincts de BODY ; ne pas appeler ses helpers de grant. Sous guard_owner avec preuves d'auth, recharger la ligne BodyConsent(populate_existing). Token opaque HMAC-SHA256 du tuple owner/type/wording/granted/granted_at/withdrawn_at ; absence explicite signée, pas wording pris pour génération.

Chaque changement réel produit un timestamp UTC microseconde strictement supérieur à max(nowUTC, granted_at, withdrawn_at) : si égal/antérieur, max+1microseconde. Une actiongrantactualise granted_at, une révocationwithdrawn_at, conserve l'autre ; dates rechargées depuisSQLite pour le token. Ainsi révoquer/réaccorder sous horloge figée ne réaccepte pas le token d'avant. Dépassement de représentation refuse sans effet. Même état/wording refusé comme no-op, sans timestamp fabriqué pour une action inexistante. TokenCAS vérifié sous même garde ; deux écritures concurrentes ne gagnent pas ensemble. Aucun reçu historique d'accord promis : réponse perdue→GET état courant/wording/token. Permission fraîche exigegrantedtrue ET wordingversionexact. GrantBODY seul et grantNUT obsolète refusés. Le modèle BODY commun est support de stockage, pas transfert de finalité.

## Revue technique — identité et vocabulaire figés après reproduction
Les jetons de tête, accord, curseur et read_id lient désormais explicitement le backend immuable `NUTRITION_BACKEND_IDENTITY` et le schéma `nutrition_manual_01`. Signature propre `NUTRITION_SIGNING_KEY` (minimum32caractères), aucune valeur/reprise par défaut du hostname ou du secret général. Ces deux paramètres doivent être provisionnés séparément par banc ; copie d’un backend vers un autre exige une identité distincte. Absence refuse503, sans startupDDL ni activation implicite. Les changements de secret/identité invalident les anciens jetons ; traiter cette rotation comme opération contrôlée, pas dépannage silencieux.
Le vocabulaire externe est fermé : auth401 ; consent_required/acquisition_unavailable403 ; foreign_or_missing404 ; unsupported_contract406 ; stale_head/stale_target/stale_consent/idempotency_mismatch409 ; invalid_command422 ; storage_unavailable503. `stale_consent` identifie le CAS propre de l’accord, `acquisition_unavailable` le flag fermé, sans les confondre avec un refus utilisateur. `no_change` demeure interne et est projeté invalid_command422. Ce complément remplace la liste abrégée R2 ; le client n’invente jamais un effet à partir d’un refus ou d’une erreur inconnue.
