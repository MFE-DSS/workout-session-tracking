# NUT-01 — persistance, ownership et commandes figés pour revue

12 novembre 2026. PROPOSED / NO_GO_BUILD. Complète le design manuel restauré du11novembre, même change. Pas migration appliquée ni produit réalisé. Base canonique3cf77e1 ; future migration après BODY `body_measurement_operations_01`, uniquement une fois ce parent fusionné et vérifié.

## Décisions techniques proposées
Deux tables append-only portent les états ET leurs reçus ; pas de table de totaux parallèle. Les valeurs JSON du contrat sont des nombres décimaux typés kcal/g ; stockage entier en milli-unités (1kcal ou1g =1000 unités). De0 à999999999 milli-unités, trois décimales maximum : limite de représentation/transport, jamais fourchette nutritionnelle recommandée. Refuser bool, nonfini, négatif, plus de trois décimales et dépassement, sans arrondi ni saturation. Source des nombres USER_DECLARED seulement. Les clés numériques/null explicite/absence sont distinguées avant canonicalisation ; corps JSON exact normalisé selon version documentée, SHA256 UTF-8, clés triées et séparateurs fixes. Un client ne recalcule pas la commande après sa sauvegarde durable.

## Tables et clés

`nutrition_target_revisions_v1` : id INTEGER PRIMARY KEY AUTOINCREMENT ; user_id FK users.id ON DELETE CASCADE ; variant enum STANDARD/TRAINING/REST ; effective_from jour ISO ; revision entier positif ; parent_ref nullable ; enabled bool strict ; kcal_milli/protein_milli/carbohydrate_milli/fat_milli nullable ; provenance JSON fermée ; request_id texte<=64 ; command_digest64 ; receipt JSON ; recorded_at UTC serveur.

Contraintes : UNIQUE(user_id,id), UNIQUE(user_id,variant,effective_from,revision), UNIQUE(user_id,request_id), UNIQUE(user_id,parent_ref) lorsque parent nonnull. FK composite(user_id,parent_ref)→(user_id,id), NO ACTION DEFERRABLE INITIALLY DEFERRED. Parent même variant/date contrôlé dans transaction. revision1 iff parentnull ; plus grandes révisions parent réel immédiatement précédent. enabled exige au moins une valeur connue ; enabledfalse exige quatre valeursnull. Les contraintes bool/range/longueurs sont SQL CHECK ET validation serveur. Index(user_id,variant,effective_from,revision). Cible datée future permise comme programmation explicitement choisie, aucune recommandation initiale.

`nutrition_day_revisions_v1` : id INTEGER PRIMARY KEY AUTOINCREMENT ; user_id FK users.id ON DELETE CASCADE ; local_day jourISO ; timezone IANA ; revision entier positif ; parent_ref nullable ; state ACTIVE/WITHDRAWN ; declared_complete boolstrict ; quatre valeurs *_milli nullable ; target_ref nullable ; provenance JSON fermée ; request_id<=64 ; command_digest64 ; receipt JSON ; recorded_at UTC.

Contraintes : UNIQUE(user_id,id), UNIQUE(user_id,local_day,revision), UNIQUE(user_id,request_id), UNIQUE(user_id,parent_ref) lorsque parentnonnull. FK composite(user_id,parent_ref) vers la même table ; FK composite(user_id,target_ref) vers nutrition_target_revisions_v1(user_id,id), toutes deux NO ACTION DEFERRABLE INITIALLY DEFERRED. user_id NOT NULL empêche référence étrangère. Parent même jour et révision précédente vérifié sous verrou. ACTIVE exige au moins un nombre ; WITHDRAWN exige quatre valeursnull, target_refnull et declared_completefalse. Les révisions historiques sont conservées. Index(user_id,local_day,revision). local_day/TZ valides et jour nonfutur dans cette zone vérifiés serveur ; pas de date de repas/instant inventé.

Les FK différées évitent de bloquer une suppression de compte transactionnelle qui retire toutes les lignes liées ; leur compatibilité avec le producteur d'effacement est à tester. Aucun effacement personnel n'est activé par ce scope synthétique. Pas de ON DELETE SET NULL qui pourrait réécrire silencieusement une référence historique. Migration neuve sans UPDATE/backfill, sans DDL startup ; downgrade seulement si les deux tables sont vides, sinon refus fermé et rollback applicatif compatible conservant schéma/lecteurs.

## Mutations et concurrence
Namespace fermée DAY ou TARGET, chemins/intent fermés. Auth Bearer + identité backend/compte vérifiées à chaque frontière. Support SQLite seulement pour l'acquisition de ce scope ; dialecte non prouvé refuse les writes, pas mutex mémoire substitué.

Ordre : validation structure/finite/taille → transaction owner guard SQLite (réemploi de l'interface publique existante, pas de copie de politique) → lookup(user,namespace,request_id) → digest identique : reçu historique exact, divergent409 → consentement nutrition applicable et flag synthétique → lecture de tête propriétaire → token CAS → validation acquisition → INSERT état/révision/reçu atomiques → commit. Aucun nouvel effet avant receiptlookup ; ancien reçu ne donne pas permission actuelle de lire/écrire les faits. Échec FK, CAS ou commit : rollback sans demi-journal. Aucun receipt exposé par une autre namespace/owner.

Token de tête opaque lié à owner + domaine + clé logique + dernière id/revision ; absence de tête a un token explicite propriétaire pour créer. Création concurrente : une seule tête1 ; original et parent immuables. Aucun UPDATE des anciennes révisions.

DAY intents : SET_FIELDS (patch seuls quatre nombres/TZ explicitement confirmée), SET_TARGET_REF (référence exacte ou null), COMPLETE (action explicite bool), WITHDRAW (geste explicite). Un body peut confirmer complétude avec les valeurs de son aperçu exact, sous même CAS ; sinon tout changement d'apports remet false. L'absence de champs préserve, null efface ; aucun no-op artificiel. Un jourWITHDRAWN peut être rouvert seulement par SET_FIELDS explicite avec de vrais chiffres sous tête courante ; anciennes révisions restent auditables. Nouveau jour doit être choisi, aucune copie automatique.

TARGET intents : SET_FIELDS/ DISABLE, variante et effective_from explicites. Correction d'une clé existante garde variante/date ; créer une date d'effet différente crée une autre clé et ne déplace pas l'ancienne. Pour un jour, résoudre d'abord la date d'effet maximale<=jour, puis la dernière révision de CETTE clé. Si disabled, aucun fallback vers une ancienne cible. Le candidat n'est jamais associé automatiquement : le jour garde seulement l'id exacte acceptée. Nouvelle cible ne réécrit aucune journée. Référence proposée doit être owner-bound, enabled et applicable au jour au moment de la sélection ; son usage historique reste lisible après désactivation ultérieure.

## Accord, lecture et complétude
Finalité technique `nutrition_manual`, versiondewording1, séparée de body_measurements. GET/POST d'état d'accord via BodyConsent sous CAS ; aucune case précochée/grant de fixture produit. Accord corporel seul ne permet rien. Révocation bloque acquisition fraîche et cibles, mais pas lookup minimal du reçu historique exact sous auth. Lecture de faits/export selon permission explicitement définie : pour le banc, accord courant requis ; accord requis n'est jamais liste vide. Réponse perdue d'accord se résout par GET état/version, sans inventer un reçu d'ancienne commande.

Pour une période inclusive<=366jours, heads seulement ; cibles historiques par ref exacte. Par champ : somme des valeurs connues, nombre de jours connus et couverture ; jours absents/retirés/partiels/terminés distingués. Journal déclaré complet avec champnull reste nombre inconnu. Moyenne, si exposée, porte seulement ses jours connus et le dénominateur exact ; aucun lissage/trend prédictif. Pas de ratio ou couleur normative. Comparaison apport/cible limitée aux paires champ/jour connues, ref incluse ; overflow de somme/différence retourne valeurnull + UNKNOWN_ARITHMETIC_RANGE, pas zéro/Infinity. Pas de double compte des versions.

## Local et recovery
Une table `nutrition_pending_commands_v1` sur le journal possédé, colonnes de copie opérationnelle : owner_ref/backend_ref/namespace/request_id uniques, méthode/path/bodycanonique/digest/token, état PREPARED/SENT_UNKNOWN/ACKED/CONFLICT, reçu exact et timestamps techniques. Aucune deuxième chronologie nutrition. Namespace n'est jamais SQL libre.

Commit local puis relecture exacte avant HTTP ; panne storage interdit l'envoi. SENT_UNKNOWN avant transport. Reprise : GET status d'abord ; reçu vérifié owner/namespace/request/digest/effet et ACK durable avant refresh. Status404 reste incertain, replay explicite du même body/clé, jamais nouvelle clé automatique. Authrefresh vers un autre owner, logout et changement backend invalident émission/réponses tardives. Kill/offline/reconnect ne créent pas de permission. Pas d'outbox de séries réutilisée et pas de job background nutrition.
