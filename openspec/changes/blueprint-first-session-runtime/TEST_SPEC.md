# Test specification — PLAN V3 runtime

**Tests futurs à écrire après GO BUILD ; aucun test produit ajouté/exécuté par cette préparation.** Les noms et assertions ci-dessous constituent les oracles d’implémentation, pas des résultats obtenus. Un résultat positif vient du vrai producteur/registre/validateur admis livré par SCI ; aucune fixture READY locale ne le remplace. SCI PR375 fournit déjà isolément les deux états positifs et deux négatifs décrits dans son AGENT_HANDOFF/manifeste ; cela ne satisfait aucun des tests runtime futurs ci-dessous et sa livraison canonique est vérifiée sur d7de8aa (quatre CI réussies).

## Harness and evidence

Backend : application FastAPI réelle de test, Bearer de deux propriétaires, DB transactionnelle, migrations additives appliquées ; requêtes HTTP réelles via client de test. Tests de concurrence sur connexions distinctes et barrières d’exécution avant commit, SQLite réellement et PostgreSQL lorsque supporté. Pas de mock du verrou ou du producteur dans la preuve positive. Scénarios de transport : coupure après commit, réponse perdue, redémarrage du consommateur, renouvellement auth et changement de compte.

Mobile : adaptateurs/contrôleur V3 réellement composés, auth.revision/outbox/stockage persistants, tests HTTP intégrés selon infrastructure native. Doubles de transport permis pour retards/fautes déterministes, distincts des preuves backend du moteur réel. Suites V1 inchangées rejouées ; aucun fixture de protocole importé dans le runtime.

## Completion evidence rule

L’exécuteur cite pour chaque preuve le HEAD, les commandes/runs réels, résultat attendu/obtenu et limites. Tests SCI isolés prouvent l’autorité scientifique, pas un compte/transport/commande. Tests de schéma seuls ne ferment rien. Cette spécification n’affirme aucune des37preuves acquise.
