### Le désaccord que rien ne révélait

Le lock déclarait `# autogenerated by pip-compile with Python 3.14` pendant que
la CI tournait en 3.11. Personne ne s'en apercevait **parce que rien
n'installait le lock**. Le jour où quelque chose l'installe, ce désaccord devient
un incident.

`docs/SECURITY_BASELINE.md` §5.3 avait d'ailleurs posé les trois préconditions de
bascule dès `Sb_26.4`. Ce sprint les tient (§4).

## 2. Brainstorming / Options / Risques / Choix (CLAUDE.md §3)

**Option A — figer le lock tel quel et le rendre autoritaire.** Rejetée après
mesure : le lock était périmé de 13 paquets sur 29. La CI installe aujourd'hui
les **dernières** versions compatibles ; figer l'ancien instantané l'aurait fait
**régresser** vers des versions qu'elle n'a jamais testées ensemble. Rendre le
lock autoritaire ne doit pas être un downgrade déguisé.

**Option B — régénérer avec `pip-compile` en local.** Rejetée : `pip-compile`
résout pour l'interpréteur courant. Depuis un shell 3.14, il produit un lock 3.14
— exactement le défaut d'origine, reconduit.

**Option C — retenue : régénérer *pour* 3.11 avec `uv`, à la résolution
courante.** `uv pip compile --python-version 3.11` résout pour une cible
différente de l'interpréteur. Le lock fige alors **ce qui tourne déjà**, pas un
instantané ancien.

**Risque principal** : le lock épingle des versions que je ne peux pas tester en
local (§6). La CI réelle est le seul juge, et le tier `CI_INFRA` l'exige de toute
façon.

## 3. Le changement

**Avant**

```
requirements.txt   →  pip install (CI × 2, VPS)      ← plages ouvertes
requirements-lock  →  pip install --dry-run          ← advisory, continue-on-error
```

**Après**

```
requirements.txt   →  SOURCE SPEC (plages, éditée à la main)
requirements-lock  →  INSTALL CONTRACT — CI × 2, VPS, et pip-audit
                      + check_lock_drift.py, bloquant
```

| Fichier | Changement |
|---|---|
| `requirements-lock.txt` | régénéré **pour Python 3.11** à la résolution courante |
| `.github/workflows/ci.yml` | 2 installs → lock · étape advisory → garde bloquante · `pip-audit` → lock |
| `scripts/deploy_prod.sh` | install → lock, avec échec explicite si absent |
| `scripts/regen_lockfile.sh` | cible 3.11 explicite, `uv` prioritaire, **refus** si `pip-compile` tourne sous un autre interpréteur |
| `scripts/check_lock_drift.py` | **neuf** — garde hors ligne |
| `docs/SECURITY_BASELINE.md` | §5 réécrite : *advisory* → **autoritaire** |

### Commandes utilisées

```bash
uv pip compile --python-version 3.11 --strip-extras --upgrade \
    --output-file requirements-lock.txt requirements.txt
```

`--upgrade` **une fois**, délibérément, pour aligner le lock sur la résolution
réelle. Le script ne le porte **pas** par défaut : une régénération après ajout
d'un paquet ne doit pas bousculer tout l'arbre au passage.

### Ce que le lock a gagné

29 paquets, 16 versions actualisées — `fastapi` 0.136.3 → **0.141.1**,
`starlette` 1.3.1 → **1.6.0**, `sqlalchemy` 2.0.50 → **2.0.52**, `uvicorn`
0.49.0 → **0.52.3**. `bcrypt` reste **4.3.0** : la borne `<5` tient, et un test
le vérifie — passlib 1.7.4 ne sait pas charger bcrypt 5.

**Ces versions ne sont pas nouvelles pour la CI** : elle les installait déjà à
chaque run depuis les plages ouvertes. Le sprint ne change pas ce qui tourne, il
**empêche que ça change en silence**.

peut le faire, et c'est précisément ce que le tier `CI_INFRA` exige.

## Verdict

**LOCK AUTORITAIRE — CI et production installent le même fichier.**

Le défaut n'était pas le lock périmé : c'était que **rien ne le lisait**. La
pipeline épinglait le code à un SHA exact tout en laissant l'arbre de dépendances
se résoudre à chaque installation ; deux déploiements du même SHA pouvaient
livrer des bibliothèques différentes. C'est le seul trou de la propriété dont
cette pipeline tire sa valeur.

Deux décisions ont porté le sprint. **Régénérer pour 3.11 et non pour
l'interpréteur local** — sans quoi j'aurais reconduit le défaut d'origine sous
une autre forme. Et **figer la résolution courante plutôt que l'ancien
instantané** — figer un lock périmé aurait fait régresser la CI vers des versions
qu'elle n'a jamais testées ensemble, en croyant améliorer la reproductibilité.

Ce que le sprint ne prouve pas localement : que les versions verrouillées font
tourner l'application. La CI réelle en décide, et c'est écrit plutôt que sous-
entendu.
